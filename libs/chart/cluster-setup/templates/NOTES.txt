   That is the expected state for exactly one install. A frontend is a
   DynamoGraphDeployment in either topology, and that CRD is applied by the Dynamo
   operator at runtime rather than shipped in this chart, so the very first install
   of a new cluster has to render none. Name the topology in a second pass, once
   the operator above is running — together with the agent, which is refused
   without a frontend:

     helm upgrade {{ .Release.Name }} <chart> -n {{ .Release.Namespace }} --reuse-values \
       --set frontend.mode=per-model --set agent.enabled=true

   per-model gives each model its own frontend on its own image (ADR 0013); shared
   gives the cluster one that every model must be servable by. Pick before the
   first model lands: changing it later means deleting and re-rendering every
   graph, and every model reloads its weights.

Watch the operator come up and enrol:

  kubectl -n {{ .Release.Namespace }} rollout status deploy/hangar-operator

The first handshake promotes the cluster from `pending` to `active` and stamps
`enrolled_at`, so there is nothing to do here for an install that reached the hub.
It happens once and only out of `pending`, which is what keeps it from fighting an
operator who has since moved the cluster to `draining` or `disabled`.

Check it rather than assuming it, because the phase is what decides whether this
cluster can serve at all — endpoints resolve only on a phase that may serve, so a
cluster left `pending` is absent from the gateway's routing table and its models
answer as though they were nowhere:

  GET /v1/clusters/{{ .Values.cluster.id }}     -> phase, reachable, sync.state

If it is still `pending`, the handshake has not happened — read the operator's logs
rather than setting the phase by hand. Should you need to anyway:

  PATCH /v1/clusters/{{ .Values.cluster.id }}   {"phase": "active"}
